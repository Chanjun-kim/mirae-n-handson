# 레거시 모듈 문서화

## 원칙
- 분석 대상 폴더(`legacy/...`)와 `db/` 의 파일은 읽기만 한다. 수정 · 생성 · 삭제하지 않는다.
- 모든 주장에 `파일:줄번호` 근거를 단다. 근거를 못 대면 쓰지 않거나 "확인하지 못함"으로 남긴다.
- 단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어간다.

## 0. 대상 · 산출물 정하기
- `<모듈명>` 은 폴더 이름이 아니라 다음 셋 중 하나다.
  `legacy/item-bank-php` → `item-bank`, `legacy/assignment-thymeleaf` → `assignment`, `legacy/grade-mssql` → `grade`.
- 산출물: `docs/<모듈명>/ARCHITECTURE.md`, `docs/<모듈명>/ERD.md`, `docs/<모듈명>/BUSINESS-RULES.md`.
- 범위 제한 인자가 있으면 그 범위만 다루고, 각 문서 머리말에 분석 범위를 적는다.

## 1. 계획 먼저 제시
- 파일 목록(`ls -R` · Glob)과 파일별 줄 수를 확보한다. 목록 명령이 실패하면 파일명을 추측하지 말고 멈춰서 알린다.
- 읽을 파일 · 단계 순서 · 산출물 경로를 계획으로 보여 주고, 승인을 받은 뒤 시작한다.

## 2. 진입점 → ARCHITECTURE.md 저장
- URL · 화면 · 배치 등 외부에서 처음 실행되는 파일과 그 근거(라우팅 · Dockerfile · compose)를 표로 적는다.
- 모듈 개요와 폴더 구조(파일별 줄 수 · 역할)를 함께 적는다.

## 3. 의존 관계 → ARCHITECTURE.md 에 추가 저장
- include · import · 함수 호출을 실제 코드에서 따라가 호출 방향(A → B)을 적는다.
- 외부 라이브러리(`vendor/` 등)는 사용법만 확인하고 내부는 분석하지 않는다.

## 4. 데이터 흐름 → ERD.md 저장
- SQL(SELECT · INSERT · UPDATE · DELETE)이 나오는 줄을 모두 찾아 테이블 · 컬럼 · 뷰별로 정리한다.
- 테이블 · 뷰 정의는 `db/` 의 스키마까지 따라가 읽는다. 모듈 밖이라고 "미확인"으로 두지 않는다.
- 화면 입력 → 검증 → SQL → 출력 흐름을 화면별로 적는다.

## 5. 비즈니스 규칙 후보 → BUSINESS-RULES.md 저장
- 조건문 · SQL 조건 · 상수 · 정렬 · 페이지 · 검증 · 상태 값을 규칙 후보로 뽑는다.
- 머리말에 "코드를 읽어 뽑은 후보이며 실행해 확인하지 않았다"와 확신도 기준을 적는다.
  - 확실: 조건문 · SQL 로 확인했다. / 추정: 이름 · 주석으로 짐작했다.
- 규칙 하나는 아래 형식을 그대로 쓴다.

```markdown
### BR-01 <규칙 한 줄 제목>
- **규칙:** <무엇이 언제 어떻게 되는지>
- **근거:** `search.php:522`, `01-schema.sql:70`
- **근거 코드:**
  ```php
  <해당 줄을 그대로 인용>                      // search.php:522
  ```
- **확신도:** 확실 | 추정
- **비고:** <매직 값, 중복 구현, 주석과 코드 불일치, 경계값 등>
```

## 하지 말 것 (item-bank 검증 이력에서 실제로 틀렸던 유형)
- 뷰 · 테이블 정의를 `db/` 에서 읽지 않고 "뷰가 무엇을 거르는지 미확인"으로 남기기. 스키마 줄까지 근거로 댄다.
- 주석 문구를 동작으로 쓰기. 예: "대개 0건"은 주석(`search.php:250`)에만 있었다. 주석만 근거면 확신도는 "추정"이다.
- 한 입력의 처리를 다른 입력에 일반화하기. 예: 검색 값은 trim 하지만 `page` 는 trim 하지 않는다(`search.php:337`). 입력마다 줄을 확인한다.
- 타입 변환 결과를 짐작하기. 예: `(int)` 변환이면 `abc` → 0, `2.7` → 2(`search.php:228`). 변환 코드를 인용해 결과를 적는다.
- 두 층의 비교 기준을 하나로 합치기. 예: PHP `===`(`search.php:253`)와 SQL 컬레이션 비교는 기준이 다르다. 따로 적는다.
- 디렉터리 목록 없이 파일명을 추측해 읽고 "기능이 없다"고 단정하기. "없다"는 목록 · 메뉴 · grep 근거를 함께 댄다.
- 경계 사례 빠뜨리기. 예: 문항 0개인 단원도 목록에 나옴(`units.php:16-19`), 빈 난이도도 오류(`register.php:44`, `:70`).
- 존재하지 않는 함수 · 파일 이름을 쓰거나, 호출 방향을 코드 확인 없이 적거나, 코드에 없는 규칙을 "그럴 것이다"로 만들기.

## 6. 마무리 — 사람이 표본 점검할 규칙 3개 추천
- BUSINESS-RULES.md 에서 규칙 3개를 골라 답변에 ID · 이유와 함께 추천한다.
  - 1개는 **가장 그럴듯해서 그냥 믿기 쉬운 규칙**(이름 · 주석에 기대거나 상식과 맞아 보이는 것).
  - 나머지는 확신도 "추정" 규칙, 여러 파일(코드 + 스키마)을 엮어 판단한 규칙에서 고른다.
- 점검 방법(읽을 `파일:줄번호`)을 규칙마다 한 줄로 적는다.
- 사람이 점검한 결과는 BUSINESS-RULES.md 끝 "검증 이력" 표(항목 · 판정 · 반영)에 남긴다.
