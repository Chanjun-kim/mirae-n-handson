# 승인 체크리스트 v1

v1 · 2회차 (2026-10-06)

오늘 바뀐 점:
- 판단이 필요하던 네 항목("충분하다" · "심각한 문제" · "지나치게" · "적절하게")을 예/아니오로 답하는 문장으로 바꿨다.
- 치명 이슈를 비밀값 노출 · 데이터 손실 · 인증 우회 · SQL 문자열 조립 네 가지로 한정했다.
- 컨벤션 위반을 반려 항목(계층 규칙 · 빈 catch · 임시 출력)과 경고 항목(네이밍)으로 나눴다.

AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다. 네 기준이 **모두** 충족되어야 승인이다. 하나라도 미충족이면 반려.

모든 항목은 "예 / 아니오"로 답한다. "아니오"가 하나라도 있는 기준은 미충족이다. 단, "(경고)"로 표시한 항목은 "아니오"여도 기준을 미충족으로 만들지 않는다.

## 심각도 정의

- **치명** — 다음 네 가지 중 하나에 해당하는 문제. 1건이라도 있으면 반려. 그 밖의 문제는 치명으로 올리지 않는다.
  - 비밀값 노출: 비밀번호 · 토큰 · 키가 코드 · 설정 · 테스트 픽스처 · 로그에 리터럴로 들어 있다.
  - 데이터 손실: 요청에 명시되지 않은 삭제 · 덮어쓰기 코드가 있다.
  - 인증 우회: 인증 · 권한 검사를 지우거나 건너뛰게 바꿨다.
  - SQL 문자열 조립: 입력값을 문자열로 이어 붙여 SQL 을 만든다.
- **경고** — 치명은 아니지만 다음 변경에서 사고가 될 수 있는 문제. 경고만으로는 반려하지 않는다. 이슈 목록에 남긴다.
- **제안** — 더 나은 방법이 있다는 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다.

## 1. 테스트 통과

- [ ] 변경된 모듈의 테스트 명령을 실제로 실행했다(실행하지 않고 통과라고 쓰지 않는다).
- [ ] 실행 결과에 실패 · 오류가 0건이다.
- [ ] 새로 추가된 public 메서드마다 그 메서드를 호출하는 테스트가 1개 이상 있다(getter · setter · 생성자 같은 접근자는 제외).
- [ ] 기존 테스트를 지우거나 건너뛰게(`skip`, `@Disabled`) 바꾼 곳이 없다.

## 2. 치명 이슈 0건

- [ ] 비밀번호 · 토큰 · 키가 코드 · 설정 · 테스트 픽스처 · 로그에 리터럴로 들어 있지 않다.
- [ ] SQL 을 문자열로 이어 붙여 만드는 곳이 없다(파라미터 바인딩 사용).
- [ ] 데이터를 지우거나 덮어쓰는 코드가 새로 생겼다면 요청에 그 내용이 명시돼 있다.
- [ ] 인증 · 권한 검사를 지우거나 건너뛰게 바꾼 곳이 없다.

## 3. 요청 범위 이탈 없음

- [ ] 요청 문장이 한 문장으로 확인되었다(없으면 판정하지 않고 먼저 묻는다).
- [ ] 변경 파일 목록의 모든 파일이 요청 문장으로 설명된다.
- [ ] 요청 문장으로 설명되지 않는 변경은 요청으로 고친 파일 안의 import 정리뿐이다.
- [ ] 의존성 추가 · DB 스키마 변경 · 설정 파일 변경이 있다면 요청에 포함돼 있었다.

## 4. 컨벤션 준수

- [ ] 팀 `CLAUDE.md` 의 코딩 컨벤션과 금지 사항을 대조했다(`convention-check` Skill 이 있으면 그 결과를 쓴다).
- [ ] 계층 규칙 위반이 없다: 컨트롤러에서 Repository · SQL 을 직접 호출하는 곳이 없다.
- [ ] 빈 catch 가 없다: 예외를 잡고 아무 처리 없이 넘기는 곳이 없다.
- [ ] `System.out.println` · `console.log` 같은 임시 출력이 남아 있지 않다.
- [ ] (경고) 클래스 · 메서드 · 상수 이름이 팀 `CLAUDE.md` 의 네이밍 규칙을 따른다. 어긴 곳은 경고로 이슈 목록에 적는다.

## 판정 형식

첫 줄에 `판정: 승인` 또는 `판정: 반려`. 이어서 네 기준의 충족 · 미충족 표, 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향). 코드는 수정하지 않는다.
